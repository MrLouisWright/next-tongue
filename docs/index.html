01 · The problem

Next.js 16 changed the rules.

Next.js 16 made Cache Components and Partial Prerendering the way to build fast apps, and renamed middleware to proxy.ts. Existing i18n libraries were designed before that, and it shows.

next-intl

Excellent and mature, but reading the locale in cached/static scopes has been a long-running pain point, as have proxy.ts locale routing and dynamicParams = false SSG.

next-international

No release since October 2024.

next-intl 4.8+ precompile

Compiles ICU at build time, but the client still receives catalogs through the provider.

Paraglide JS 2

Proves the compiler approach with typed, tree-shaken message functions, but its Next plugin requires --webpack.

A Next.js 16–only i18n library that compiles ICU messages ahead of time and works with Turbopack, the default bundler. Client components ship only the messages they actually call. The locale comes from route params, never from headers, so translated pages stay in the static shell under Cache Components.

02 · How it works

A config wrapper, codegen and a per-file loader.

1

Codegen before bundling

tongue build (or withTongue when next.config loads) parses messages with its own ICU parser, validates plurals and arguments, and writes .tongue/types.d.ts, per-key modules and a manifest.

2

Per-file call-site loader

A Turbopack/webpack loader rewrites t('inbox') in client files into a static import of #tongue/msg/home/inbox. No bundler plugin APIs.

3

Only what you call ships

The bundler dedupes and tree-shakes per key across routes. Translating on the server and passing strings ships no message code at all.

Design principles

  1. Build time over run time. If it can be parsed, validated, typed or tree-shaken at build time, it is. ADR 0001
  2. The locale is a route param. Only proxy.ts touches headers and cookies, so every translated scope can be cached and prerendered. ADR 0002
  3. Standards, not lock-in. ICU MessageFormat, plain JSON files, any OpenAI-compatible model, MIT license.
  4. Next.js-native, nothing else. Next.js 16+ App Router only, latest minor supported, with a nightly canary run. ADR 0006
  5. Zero dependencies. Nothing beyond the next and react peers, at runtime, build time or in the CLI. ADR 0012

03 · Features planned

Everything in the README, nothing more.

Zero dependencies

Own small ICU parser with a documented subset, Node built-ins only in the CLI, enforced by a CI dependency budget.

Compiled, works with Turbopack

Codegen before bundling plus a per-file call-site loader; no bundler plugin APIs.

Client ships only what it calls

Each t() call imports a per-key module. Translate on the server and pass strings to ship no message code at all.

Params-only locale

The locale always comes from route params (resolved by proxy.ts), never from headers() or cookies() inside cached scopes. Static shells, PPR and output: 'export' work.

Fully typed

Keys, namespaces and ICU arguments ({count, plural, ...} → count: number) are checked by TypeScript.

Database and CMS messages

Async build-time sources in tongue.config.ts, compiled and typed like files, plus server-only formatMessage for copy that changes without a rebuild.

Translator-friendly tooling

en-XA pseudo-localisation, tongue export/import for XLIFF 2.0 and CSV, and a per-route report of keys and bytes sent to the client.

One API across the App Router

Server components, client components, server actions, generateMetadata with hreflang, translated OG images and emails, locale-aware Link, redirect and useRouter.

CLI on Node built-ins

tongue build, init, extract, check (CI gate for missing, unused and mismatched keys) and translate with any OpenAI-compatible endpoint.

Hydration-safe dates

An explicit timeZone in config (default 'UTC'). The server's default zone is never used.

Accessible LocaleSwitcher

Headless, keeps the same page with localized pathnames, persists the choice, works without JS.

Security-hardened

XSS tests for rich text and database strings, strict locale validation against path traversal and header injection, and a threat model.

04 · Quick start planned API

From install to typed output.

// tongue.config.ts
import { defineConfig } from 'next-tongue/config';

export default defineConfig({
  locales: ['en', 'de'],
  defaultLocale: 'en',
  messages: './messages/{locale}.json',
});
// next.config.ts
import { withTongue } from 'next-tongue/next'; // config wrapper: runs codegen, registers the call-site loader
export default withTongue({ cacheComponents: true });
// proxy.ts
import { createProxy } from 'next-tongue/proxy';
export const proxy = createProxy();
export const config = { matcher: ['/((?!api|_next|.*\\..*).*)'] };
// Note: this matcher skips every path containing a dot (e.g. /de/blog/v1.2). See Routing & proxy.
// messages/en.json
{ "home": { "title": "Welcome, {name}!", "inbox": "{count, plural, =0 {No messages} one {# message} other {# messages}}" } }
// app/[locale]/page.tsx
import { getT } from 'next-tongue/server';

export default async function Page({ params }: PageProps<'/[locale]'>) {
  const { locale } = await params;
  const t = await getT(locale, 'home');
  return <h1>{t('title', { name: 'Ada' })}</h1>; // t('titel') or a missing `name` is a type error
}
// app/[locale]/inbox-badge.tsx
'use client';
import { useT } from 'next-tongue/client';

export function InboxBadge({ count }: { count: number }) {
  const t = useT('home');
  return <span>{t('inbox', { count })}</span>;
}

06 · FAQ

Straight answers.

From docs/faq.md. Something missing? Open an issue.

Is this usable today?

Beta 0.9 (API freeze). Install from git until npm publish; see the releasing doc and roadmap.

Why not just contribute to next-intl?

next-intl is great and mature. next-tongue explores a different core trade-off (build-time compilation that works with Turbopack, message-level client tree-shaking, params-only locale and zero dependencies) which would be a breaking redesign there. A migration guide exists; a next-intl codemod is planned after v1.0.

Why not Paraglide?

Paraglide pioneered compiled, tree-shaken messages and documents a Next.js 16 setup with Cache Components, but its Next plugin requires --webpack. next-tongue applies the compiler idea with a Turbopack-compatible loader and Next.js-specific pieces built in: proxy.ts routing, metadata/hreflang, tongue check.

Does it require Cache Components?

No. It works with or without cacheComponents: true; it just never breaks it.

Can I load messages from a database or CMS?

Yes, two ways: async build-time sources in tongue.config.ts (compiled and typed like files, need a rebuild to change), or the server-only formatMessage(locale, icu, values) for copy that changes at request time (untyped). No catalog is sent to the browser.

Will there be benchmarks?

Yes, in v0.1: a published bundle benchmark against next-intl (with precompile) and Paraglide is the go/no-go gate. Until then there are no size or speed claims.

Which Next.js versions?

The latest 16.x minor, tested nightly against canary. Pages Router is not supported.
